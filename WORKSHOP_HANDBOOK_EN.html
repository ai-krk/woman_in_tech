Build your Recruitment Coach

Women in Tech Insight · 120 minutes · Individual work · English

Create a small Gemini-connected coach that helps a fictional candidate prepare for an interview. You will run short Python cells, change one instruction and follow what the model actually asks your tools to do.

Illustration embedded in the executable notebook: Fictional illustration of an individual learner comparing notebook output with evidence and making her own notes.

Learning illustration: you inspect the code, check the evidence and make the final judgment.

What you will leave with

  • A coach that retrieves a role, checks supplied experience and offers a practice question.
  • Your own small change, a test and a preparation draft to fact-check.
  • A clear explanation of what the model decides and what Python executes.

def get_role(role_id):
    if not isinstance(role_id, str) or role_id not in ROLES:
        return {"status": "unsupported", "allowed_roles": list(ROLES)}
    return {"status": "found", "role_id": role_id, **ROLES[role_id]}

def get_evidence(skill):
    known = {s for role in ROLES.values() for s in role["skills"]}
    if not isinstance(skill, str) or skill not in known:
        return {"status": "unsupported", "records": []}
    records = [record for record in EVIDENCE if skill in record["skills"]]
    return {"status": "found" if records else "missing", "records": records}

C14 · S4 · Follow the agent loop

70–85 min · Required · Read the flow · ← C13 · Route · C15 →

Illustration embedded in the executable notebook: Agent loop: your goal and instructions go to Gemini; Gemini requests a tool; Python validates and runs an allowed lookup; results return to Gemini; repeat within a budget or finish with a draft for human review.

Conceptual flow, not a record of execution. Inspect your own trace at C17.

Idea. Gemini chooses tool requests. Python checks and executes them, returns results and asks the model again. The order is not hard-coded.

Do. Follow the next function from top to bottom: ask → collect calls → validate/run → return results → repeat or finish. Then run the definition.

Check. No output is expected yet: you have defined run_coach, not called it. The prepared helper handles transport and history. Each run allows at most 5 model requests and 6 tool attempts, with no automatic retries.

If stuck. Focus on the sequence. You can inspect AgentSession in the helper after the workshop. All model-accessible tools are read-only lookups.

def run_coach(request, active_client):
    session = AgentSession(request)
    for _ in range(session.max_requests):
        reply = session.ask(active_client, MODEL, INSTRUCTIONS, TOOLS)
        if reply is None:
            break
        calls = session.record(reply)
        if not calls:
            session.finish(getattr(reply, "output_text", ""))
            break
        if not session.can_execute(calls):
            break
        for call in calls:
            result = execute_tool(call.name, call.arguments)
            session.add_tool_result(call, result)
    return session.result()

Models, agents and their limits

Companion to slides 4–12 of the 120-minute Recruitment Coach workshop. Theory references checked 16 September 2026. These notes explain concepts, not current model rankings or a guarantee of API access. The technical setup and API verification notes remain in the Sources & further reading section of this handbook.

The distinctions to keep

  • Training and inference: training changes learned parameters. Our notebook uses an already trained model. Editing a coaching recipe changes the instructions in a request, not the model weights.
  • Model and agent: a model produces outputs. An agent system also controls tool use, carries results into the next request and decides when to stop. In this lab, Python enforces the tool boundary.
  • Model types and architectures: task, modality and adaptation describe different dimensions. A multimodal model can sit inside a fixed workflow or an agent system. Three skill recipes still belong to one loop.
  • Evidence and fluency: an answer can sound professional while adding unsupported details. Review the source behind each material factual claim.

2017 Transformer paper An influential architecture, not the invention of all attention mechanisms or all AI.

Regional use and deployment

Google's terms require users to be at least 18 and describe developer use for professional or business purposes. They require Paid Services when making API Clients available to users in the EEA, Switzerland or the UK. Thus a free API price is not permission to distribute a free-tier application in those regions. Storage is different from training

The terms' regional exception applies paid-service data-use provisions to EEA, Swiss and UK use, including unpaid quota. Those provisions say prompts and responses are not used to improve Google's products. Elsewhere, unpaid-service terms describe product-improvement use and possible human review. (S06)

Interaction resources are stored by default: one day on free tier and 55 days on paid tier. store=False opts out of that resource storage and prevents continuation using previous_interaction_id; it is not a universal zero-retention setting. (S07)

Separately, abuse-monitoring documentation describes 55-day retention of prompts, context and responses for policy enforcement, with possible authorized review. Do not equate “not used for general model improvement” with “never retained.” Use the supplied fictional material throughout class. (S22)

Terms used in this course

Term Meaning here A distinction that matters
Model The remote Gemini system that produces text or requests a tool call. It does not execute our local Python functions itself.
Tool A specific Python capability exposed through a name, description and argument schema. A tool is executable behavior; validate its arguments in code.
Skill recipe Reusable instructions describing a coaching task, steps, boundaries and expected output. Loading instructions does not grant new permissions or guarantee correct behavior.
Agent The model plus the application loop, available tools, history and stopping rules, allowing the model to choose next steps from feedback. A single text response or a fixed script is not automatically an agent.
Formal Agent Skill A package following the Agent Skills format, including a SKILL.md file and required metadata. Three notebook recipes are an instructional simplification, not automatically three installable Agent Skills.

These working definitions draw on S08, S15 and S16. “Agent” is used differently across products; the observable behavior of this notebook matters more than the label. The three tools and three recipes have different jobs and need not map one-to-one.

Prompt injection and evaluation

A fictional CV, job description or tool result may contain text that attempts to change the coach's instructions. Treat those passages as task data. An instruction to ignore such text helps communicate intent, but it is not a security boundary. Limit the actual tools and accessible data in code, validate function arguments, cap execution, and inspect what the tools did. These measures reduce the consequences of mistakes; they do not prove the model cannot be manipulated. (S12, S24)

Use a small, explicit evaluation sheet. These are suggested workshop checks:

Test input Evidence to inspect
Normal coaching request Relevant recipe, appropriate tool use, useful final response.
Missing evidence in the fictional profile A question or stated uncertainty, with no invented achievement.
Unknown role or malformed tool arguments A controlled error or clarification, with no arbitrary function execution.
Instruction hidden inside a job description Original coaching task retained; no unauthorized action or disclosure.
Request that repeatedly triggers tools Run stops at the configured limit and reports incomplete work honestly.
Revised recipe on the same examples Compare factual support, usefulness, tool calls and failures before and after the change.

Write expected behavior before running each case. Record the prompt, model, SDK version, tool trace, final answer and pass/fail reason. Repeat a few important cases because model output can vary. Assess the final result and the actions taken, not just polished wording. A handful of passing cases demonstrates those observations only; it cannot establish general reliability, fairness or hiring validity. This classroom approach adapts the evaluation principles in S17.

STAR means Situation, Task, Action, Result. Use it to organize truthful evidence and practice an answer. Missing facts should remain missing until supplied. Oxford's advice is a source for the technique's use here, not a claim that Oxford invented it. (S11)
